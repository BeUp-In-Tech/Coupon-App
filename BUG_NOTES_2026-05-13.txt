1) Unauthenticated IAP promotion endpoints allow promoting arbitrary deals
Severity: CRITICAL
Category: AuthZ / Business logic abuse

Summary:
- Apple/Google in-app purchase promotion routes are public.
- Service logic trusts client-provided dealId and does not verify caller identity/ownership.
- A valid store receipt can be used to promote another vendor's deal.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.routes.ts:9
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.routes.ts:10
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:129
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:164
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:296
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:312

Why this is a bug:
- `POST /payment/api/apple_in_app_purchase` and `POST /payment/api/google_in_app_purchase` have no `checkAuth(...)`.
- In both flows, `DealModel.findById(receipt.dealId/payload.dealId)` is used directly.
- Promotion and payment ownership are derived from the deal document, not from an authenticated user.

Impact:
- Unauthorized paid promotion state changes.
- Possible abuse and reputational/business damage across vendor accounts.

2) Google Play purchase replay can create repeated promotions
Severity: CRITICAL
Category: Payment integrity / Replay

Summary:
- Google purchase validation does not persist/check immutable transaction identity.
- Same valid purchase token can be replayed to create repeated paid promotions.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:296
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:347
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:366
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:373

Why this is a bug:
- `validateAndroid(...)` returns boolean only.
- No persistent uniqueness check on Play transaction/order id or purchase token.
- New internal ID is generated each time: `transaction_id: generateTransactionId()`.

Impact:
- Duplicate credits/promotions from one real purchase.
- Financial/accounting inconsistency and fraud vector.

3) Stripe failed-payment webhook path mismatches object type
Severity: HIGH
Category: Payment state machine

Summary:
- `payment_intent.payment_failed` is handled as if it were a Checkout Session.
- The failure handler searches by `stripe_session_id`, but event object id is payment intent id.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:676
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:678
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/utils/paymentHelper/paymentFailed.helper.ts:8
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/utils/paymentHelper/paymentFailed.helper.ts:10

Why this is a bug:
- The switch groups `checkout.session.expired` and `payment_intent.payment_failed`.
- Both are cast to `Stripe.Checkout.Session`.
- `paymentFailedHandler` updates by `stripe_session_id: session.id`.
- For PaymentIntent events, `session.id` is not a checkout session id.

Impact:
- Payment/promotion may remain `PENDING` instead of transitioning to FAILED/CANCELED.
- Cleanup and reporting become inconsistent.

4) Voucher decrement on Stripe success uses wrong field name
Severity: HIGH
Category: Data integrity / Voucher lifecycle

Summary:
- Voucher usage decrement query uses `code`, but schema key is `voucher_code`.
- Query likely matches nothing; voucher limit is not reduced.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/utils/paymentHelper/paymentSuccess.helper.ts:86
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/utils/paymentHelper/paymentSuccess.helper.ts:89
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/voucher/voucher.model.ts:6

Why this is a bug:
- Update criteria in success handler:
  `{ code: payment.voucher_applied, voucher_limit: { $gt: 0 } }`
- Voucher schema:
  `voucher_code: { ... }`

Impact:
- Overuse of same voucher beyond intended limit.
- Business rule bypass and revenue leakage.

5) Shop create route uploads file before auth check
Severity: HIGH
Category: Resource abuse / Middleware order

Summary:
- `multerUpload.single('file')` runs before `checkAuth(Role.VENDOR)`.
- Cloudinary upload can happen for unauthorized requests.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/shop/shop.routes.ts:13
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/config/multer.config.ts:6
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/config/multer.config.ts:29

Why this is a bug:
- Route middleware order executes multipart upload first.
- `multerUpload` uses `CloudinaryStorage` directly.
- Request can be rejected later by auth, leaving uploaded files.

Impact:
- Unauthenticated storage consumption and possible cost abuse.
- Orphaned uploads.

6) Business-rule errors in shop create become HTTP 500
Severity: MEDIUM-HIGH
Category: API correctness / Error mapping

Summary:
- `createShopService` throws plain `Error` for expected client cases.
- Global handler maps plain `Error` to 500.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/shop/shop.services.ts:37
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/shop/shop.services.ts:69
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/shop/shop.services.ts:173
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/middlewares/globalErrorHandler.ts:51

Why this is a bug:
- Examples:
  - `throw new Error('business_logo missing')`
  - `throw new Error('Shop already exists for this vendor')`
  - Duplicate key handling also throws plain Error string
- Handler branch for generic `Error` sets `statusCode = 500`.

Impact:
- Client gets internal server error for expected validation/conflict scenarios.
- Harder frontend handling and incorrect API contract behavior.

7) Pagination metadata is incorrect for filtered/search queries
Severity: MEDIUM
Category: API correctness / Query meta

Summary:
- `QueryBuilder.getMeta()` counts all documents in collection, not current filtered query.
- Some endpoints then return mismatched `meta.total` and `meta.totalPage`.

References:
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/utils/QueryBuilder.ts:97
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/utils/QueryBuilder.ts:100
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/dashboard/dashboard.service.ts:281
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:689
- /media/nayemalways/F9CF-73D1/Yepp_Marv/src/app/modules/payment/payment.services.ts:703

Why this is a bug:
- `countDocuments()` is called on model without applying current filters/search.
- In `transaction_history`, `meta.total` is overwritten manually but `meta.totalPage` remains based on wrong base count.

Impact:
- Incorrect pagination UX (wrong page counts/total records).
- Potential client-side pagination errors.

6) Replace plain `Error` with `AppError` for expected 4xx failures.
