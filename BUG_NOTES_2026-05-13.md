## 1. Unauthenticated IAP Promotion Endpoints Allow Promoting Arbitrary Deals

**Severity:** Critical  
**Category:** AuthZ / Business logic abuse  
**Status:** Unfixed / deferred until Flutter sends auth token with IAP requests

### Summary

- Apple/Google in-app purchase promotion routes are public.
- Service logic trusts client-provided `dealId` and does not verify caller identity/ownership.
- A valid store receipt can be used to promote another vendor's deal.

### References

- `src/app/modules/payment/payment.routes.ts:9`
- `src/app/modules/payment/payment.routes.ts:10`
- `src/app/modules/payment/payment.services.ts:139`
- `src/app/modules/payment/payment.services.ts:174`
- `src/app/modules/payment/payment.services.ts:305`
- `src/app/modules/payment/payment.services.ts:321`

### Why This Is A Bug

- `POST /payment/api/apple_in_app_purchase` and `POST /payment/api/google_in_app_purchase` have no `checkAuth(...)`.
- In both flows, `DealModel.findById(receipt.dealId/payload.dealId)` is used directly.
- Promotion and payment ownership are derived from the deal document, not from an authenticated user.

### Impact

- Unauthorized paid promotion state changes.
- Possible abuse and reputational/business damage across vendor accounts.

### Planned Fix

- After Flutter sends `Authorization: Bearer <token>`, add vendor auth to both IAP routes.
- Pass authenticated user into Apple/Google IAP services.
- Verify `deal.user === user.userId` before creating payment/promotion.

## 2. Google Play Purchase Replay Can Create Repeated Promotions

**Severity:** Critical  
**Category:** Payment integrity / Replay  
**Status:** Unfixed / deferred with IAP hardening

### Summary

- Google purchase validation does not persist/check immutable transaction identity.
- Same valid purchase token can be replayed to create repeated paid promotions.

### References

- `src/app/modules/payment/payment.services.ts:49`
- `src/app/modules/payment/payment.services.ts:305`
- `src/app/modules/payment/payment.services.ts:307`
- `src/app/modules/payment/payment.services.ts:321`
- `src/app/modules/payment/payment.services.ts:382`

### Why This Is A Bug

- `validateAndroid(...)` returns boolean only.
- No persistent uniqueness check on Play transaction/order id or purchase token.
- New internal ID is generated each time: `transaction_id: generateTransactionId()`.

### Impact

- Duplicate credits/promotions from one real purchase.
- Financial/accounting inconsistency and fraud vector.

### Planned Fix

- Return and persist a stable Google Play purchase identity, preferably purchase token or order id.
- Enforce uniqueness before creating a new payment/promotion.
- Keep behavior coordinated with the Flutter IAP auth update.

## Recommended Fix Order

1. Secure IAP endpoints and enforce deal ownership checks after Flutter sends auth tokens.
2. Add Google Play replay protection using stable purchase identity.
